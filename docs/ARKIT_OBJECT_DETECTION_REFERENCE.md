# ARKit Object Detection — 技術リファレンス

**目的**: ARKit Object Detection（`.arobject`スキャン→自動認識）の仕組み・制約・運用ノウハウを
一箇所に集約する。実施手順は `./AR_TECHNICAL_NOTES.md`、設計決定の経緯（教員側の管理リポジトリ）は
`melon-active/ar-solution/docs/AR_CALIBRATION_ARCHITECTURE.md`「認識方式の決定変更」節を参照。本ドキュメントは「なぜそうなるか」
「何ができて何ができないか」の技術知識層。

**作成日**: 2026-08-08

---

## 1. 概要 — ARKit Object Detectionとは何か

iOS 12（2018年）から存在する、**古典的な特徴点（feature point）マッチング方式**の物体認識機能。
実物を専用アプリ（Apple公式「Scanning and Detecting 3D Objects」等）でスキャンして`.arobject`
ファイルを生成し、そのファイルをアプリに組み込むことで、カメラ映像内に同じ物体が映ったときに
位置・回転（Pose）を返す。

**機械学習ではない。** ARKitはカメラ映像から抽出した特徴点パターンと、`.arobject`に記録された
特徴点パターンを**画像的に比較**しているだけで、物体認識AIのような汎化能力はない。
スキャンした「その個体」しか認識できない（同じ製品の別個体でも、汚れ・傷・向きの違いで
認識精度が落ちることがある）。

### Gaussian Splattingとの違い（混同注意）

| | `.arobject`（ARKit Object Detection） | Gaussian Splatting |
|---|---|---|
| 登場時期 | 2018年（iOS 12） | 2023年以降 |
| 目的 | 検出・位置推定 | 見た目の再現・表示 |
| データ表現 | 疎な特徴点群（角・エッジ・模様の変化点） | 密な放射輝度場（数十万〜数百万ガウシアン） |
| 本プロジェクトでの用途 | ARTrackedObjectManagerでの自動認識 | 将来の表示用リファレンス候補（`models/kettle/scaniverse/`に取得済み・未使用） |

両者は完全に独立した技術。Gaussian Splattingで美しい見た目を再現できても、それがARKitの
認識精度を上げることには一切つながらない。

## 2. 対象物選定基準

### 2.1 実機検証で判明した相性（2026-08-07実施）

| 対象物 | 表面特性 | 結果 |
|---|---|---|
| 急須（ステンレス製） | 金属・光沢あり | ❌ 検知失敗（`models/kettle/README.md`） |
| ペットボトル（ラベル付き） | 印刷ラベル・非光沢 | ✅ 検知成功（`models/bottle/README.md`） |

### 2.2 選定基準（一般論・Apple公式ドキュメント+実機検証の統合）

- ❌ **金属・ガラス等の光沢・反射面**: 見る角度で映り込みが変化し、「同じ特徴点」として扱えない
- ❌ **単色・無地でテクスチャの乏しい面**: そもそも特徴点密度が乏しい（布のマット面等も同様のリスク）
- ❌ **柔らかく変形する物体**（ぬいぐるみ等）: Apple公式ドキュメントでも「剛体の方が検出に向く」と明記
- ✅ **印刷ラベル・模様など非光沢でテクスチャが豊富な面**
- ✅ **卓上に収まるサイズ**（Apple公式推奨: 8〜10インチ = 20〜25cm程度が最適）
- ✅ **剛体**（形状が変化しない）

## 3. 特異点（特徴点）を間接的に増減させる方法

### 3.1 直接パラメータは存在しない

`ARReferenceObject`には`rawFeaturePoints`という**読み取り専用**プロパティがあり、スキャン後の
点群を確認することはできるが、密度・数を直接指定するAPI/UIは公開されていない
（Apple非公開のVIOアルゴリズムが自動抽出）。

### 3.2 間接的に増減する要因

| 要因 | 効果 |
|---|---|
| スキャン時の網羅性（角度・距離のバリエーション） | 多いほど蓄積される特徴点が増える |
| 対象物のテクスチャ（模様・凹凸の量） | 多いほど自動抽出される特徴点密度が上がる |
| 照明のコントラスト | 明瞭であるほど検出精度が上がる |

**結論**: 「特徴点を増やしたい」場合の唯一の実務的手段は、パラメータ調整ではなく
**対象物側の条件（テクスチャ・照明・スキャンの丁寧さ）を改善すること**。

---

## 4. 照明条件の影響・許容性

### 4.1 結論: 許容性は低い

ARKitは画像ベースの比較アルゴリズムのため、**スキャン時と検出時で照明条件（方向・強さ・色温度）が
大きく異なると検出精度が大きく落ちる**。Apple Developer Forumsでの開発者報告:

> 「朝と夜で光の方向が違うと検出がしばしば失敗する」
> 「照明を一定に保つことで最良の結果が得られるが、実世界の運用には不十分」

### 4.2 場所の変化にも弱い

対象物をスキャン時と別の場所に置き直すだけでも検出が難化・失敗するケースが報告されている
（背景・周辺光の反射なども特徴点マッチングに影響するため）。

### 4.3 本プロジェクトへの示唆

展示施設の照明が時間帯・季節・天候で変わる場合、1回のスキャンでは展示当日に認識できない
リスクがある。→ §5「複数スキャン戦略」で対処方針を記録。

---

## 5. 複数スキャン戦略（照明変化への対策）

### 5.1 技術的な裏付け

`ARWorldTrackingConfiguration.detectionObjects`は**複数の`ARReferenceObject`を同時に**
渡せる仕組み（Setで受け取る）。同じ対象物を異なる照明条件でそれぞれスキャンし、別名の
`.arobject`として複数登録すれば、ARKitは登録された全パターンと同時に照合し、
どれか1つでも一致すれば検出成功する。この手法はAppleの特許文献にも記載がある
（「Object detection using multiple three dimensional scans」）。

### 5.2 唯一の注意点: 座標系の不一致

別々にスキャンした`.arobject`は、**内部の座標原点が一致するとは限らない**
（特許文献より: 複数スキャンの座標系を一つの共通座標系に対応付けるtransformを
別途決定する必要があると明記されている——ARKitは自動で揃えない）。

### 5.3 本プロジェクトでの運用方針（2026-08-08決定）

**前提**: 展示対象（鹿剥製）は**設置後に動かない**。この前提により、複数スキャン間で
座標系を数学的に厳密一致させる必要はなく、**スキャンごとに個別検証すれば十分**と判断。

**手順**:
1. 剥製を**時間帯を変えて複数回スキャン**（朝・昼・夕方など、展示会場で実際に起こりうる
   照明変化を想定）
2. 各スキャンを個別に`.arobject`としてReference Object Libraryに登録
3. **各スキャンごとに**実機テストを行い、検出時のコンテンツ配置位置を実物と比較検証
   — 確定済み設計判断の**目標精度「1cm以内のSYNC」**（教員側の管理リポジトリ`melon-active/ar-solution/CLAUDE.md`参照）を基準に、
   感覚的な「大体合っている」ではなく実測で合否判定する
4. 1cm基準を満たさないスキャンは不採用とし、原点調整をやり直すか除外する
5. 合格したスキャンだけをLibraryに残す（不合格分は`models/kettle`・`models/bottle`と
   同様に凍結保持し、失敗の記録として残す——削除しない）

### 5.4 スキャン時の原点合わせの一貫性（推奨・保険）

上記5.3は「動かない対象物」を前提に個別検証で済ませる方針だが、念のため各スキャンの
「原点位置を調整」ステップ（ScanningAppの5ステップ中の④）では**毎回同じ物理的基準点**
（例: 剥製の特定の脚の付け根等、目視で確認しやすい一点）に合わせておくと、
座標系のズレ自体が小さくなり、5.3の個別検証で不合格になるリスクを下げられる。

**具体的な基準点の推奨（2026-10-22追記）**: 「毎回同じ基準点」の候補として**対象物の底面中央**
（バウンディングボックスの底面中心）を選ぶと、ARKitが`ARReferenceObject`の原点既定値として
採用している規約と一致する。`ObjectDetectionSpawner.cs`側のAnchor原点もこの規約を前提にしており、
スキャン時に意識的に底面中央へ合わせておけば、複数スキャン間・対象差し替え間で`contentOffset`の
再調整コストが下がる可能性がある（まだ実測で効果検証はしていない——次回複数スキャンを行う際に
各スキャンの原点をこの基準で統一し、ズレ量の分散が小さくなるか比較するとよい）。

## 5.5 未検証のオープン課題: 大型対象で全景が見えない場合の挙動（2026-10-22提起）

Apple公式推奨サイズ（8〜10インチ程度、§2.2）は、カメラ視野に対象全体が収まりやすい前提が
背景にあると考えられる。鹿の剥製・ソファー・屋外彫像など大型対象では、アップで近づくと
全景が視野に入らない場面が生じる。この時の挙動は**このプロジェクトでは未検証**:

- **推測（確度中）**: 検知・Anchor確立後は通常のARKitワールドトラッキング（VIO）が座標を支えるため、
  検知成立後にアップで寄ってもAnchor自体は外れないはず（§7の座標固定は視野と無関係に機能する設計）
- **未知**: 最初からアップ（部分視野）の状態でそもそも初回検知がトリガーされるか。
  特徴点マッチング方式（§1）なので理論上は部分視野でも十分な特徴点があれば検知できる可能性があるが、
  実証なし

**次回大型対象テスト（週末予定）での確認項目**:
1. 全景が見える距離から検知 → その後ズームイン/接近してAnchorが外れないか
2. 逆に、最初からアップ（部分視野）でカメラを向けて検知自体が成立するか

## 6. 検知に時間がかかる問題（実機検証で判明・2026-08-07）

Apple公式ScanningAppの「Test」機能では即座に認識できても、独自実装のUnityアプリでは
**継続20〜30秒以上ノンストップでカメラを動かし続けないと検知しないことがある。**

**原因**: ScanningAppの「Test」はスキャンと同一セッション内で継続追跡するのに対し、
独自アプリは新規セッションでワールドトラッキングを一から確立する必要があるため、
初動が遅い。実装のバグではなく、セッションの性質差による既知の挙動。

**対策の方向性**（未検証・今後の課題）:
- アプリ起動直後にユーザーへ「カメラをゆっくり動かしてください」等のガイダンス表示
- 展示環境の視覚的特徴（壁・床のテクスチャ）を豊富にし、ワールドトラッキングの確立を早める

---

## 7. 座標固定（World Anchor）が必要な理由

検知・コンテンツ表示が成功しても、World Anchor未実装の状態では
**「スマホを動かすとコンテンツも一緒に動いてしまう（カメラに張り付いて見える）」**症状が残る
（2026-08-07実機確認済み）。これは実装漏れではなく、ワールドトラッキングの安定度が
そのままコンテンツのブレに直結するという構造的な課題。対処は`ARAnchorManager`による
座標固定（`./AR_TECHNICAL_NOTES.md`参照）。
